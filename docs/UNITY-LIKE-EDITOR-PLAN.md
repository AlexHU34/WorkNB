# NEBULA Studio — визуальный редактор 3D-игр в HTML

> Задача: сделать браузерный аналог Unity поверх нашего движка E3.
> Цель — не копия Unity, а то, чего у Яндекс Игр **нет вообще**:
> игрок собирает 3D-игру мышью и публикует её в общий каталог.

Документ создан 2026-10-10. Источник фактов о Unity: официальная документация
Unity 6.6, раздел Web (`docs.unity3d.com/Manual/webgl-technical-overview.html`).

---

## 1. Что такое Unity на самом деле

Unity — не «рендерер». Рендеринг в нём — меньшая часть. Ценность складывается
из пяти слоёв:

| Слой | Что даёт |
|---|---|
| **Модель данных** | GameObject + Component: сцена — это объекты с поведением |
| **Редактор** | Иерархия, инспектор, гизмо, превью — видно, что получится |
| **Сериализация** | сцена и префаб сохраняются как данные, а не код |
| **Режимы** | Edit / Play: можно остановиться и посмотреть, что наделал код |
| **Конвейер** | импорт ассетов, сборка, публикация |

Отказ от любого слоя превращает редактор в «игрушку». Именно поэтому «просто
сделать как в Unity» — это дорого.

### Как Unity попадает в браузер

По документации Unity 6.6, Web-сборка — это **JavaScript + WebAssembly +
WebGL**. Цена этого решения, прямо из документации:

| Ограничение Unity Web | Следствие |
|---|---|
| AOT-компиляция, без `Reflection.Emit` | нельзя генерировать код в рантайме |
| Нет управляемых потоков, однопоточный GC | тяжёлая сцена = фризы при сборке мусора |
| Нет доступа к сокетам, нет `System.Net` | сеть только через HTTP |
| Нет доступа к файловой системе | кэш отдан браузеру |
| Нет раскладки клавиатуры по физическим клавишам | не-английские раскладки ломают управление |
| WebGL = подмножество OpenGL ES | нет compute shaders |
| Физика идёт по FP без FTZ/DAZ | результаты **не совпадают** с нативной версией |
| Сборка — несколько файлов (`.wasm` + `.data` + загрузчик) | **нужен веб-сервер**, `file://` не работает |

**Вывод, который стоит запомнить:** наш `dist/NebulaBloom.html` — **один файл,
который открывается двойным щелчком с диска**. Unity в этом смысле проигрывает
нам принципиально. Это не мелочь: офлайн-работа без сервера — это то, что
отличает нас и от Unity, и от Яндекс Игр.

Строить «Unity в браузере» на WebAssembly — ошибка. Мы уже нарисовали 100 игр
на своём движке за копейки. Нужен редактор, а не новый рендерер.

## 3. Честная оценка стоимости

Полный клон Unity — это работа на годы и команду. Так делать нельзя.
Ниже — оценка **нашего** варианта, ограниченного главной идеей.

| Объём | Оценка |
|---|---|
| Базовая сцена: иерархия + инспектор + gizmo | несколько дней |
| Сериализация сцены в JSON | 1–2 дня |
| Компоненты и их редакторы | недели, по компоненту |
| Полный Unity-уровень | годы — **не делаем** |

## 4. Что делаем (фазы)

### Фаза 0. Решение о границах — 1 день
- Сцена — данные (JSON), а не код.
- Формат сцены версионируется с первого дня, иначе старые сцены
  перестанут открываться.
- Редактор **не трогает** E3: он уже умеет рисовать. Это критично —
  иначе правка редактора ломает 100 готовых игр.

### Фаза 1. Каркас редактора — несколько дней
- Три панели: иерархия слева, вьюпорт по центру, инспектор справа.
- `E3` уже умеет превью-сцену — нужен только вьюпорт с камерой.
- Редактор живёт отдельной страницей `studio.html`, собирается
  тем же `build.py`.

### Фаза 2. Модель объектов — несколько дней
- GameObject: `id`, `transform`, `components[]`.
- Компонент: `{type, props}` — чистые данные, никакого поведения внутри.
- Поведение — **только** через BloomScript. Так граница между данными и
  кодом остаётся честной, и сцену можно сохранять и проверять.

### Фаза 3. Инспектор — по одному дню на тип
Порядок по убыванию пользы: Transform, Mesh/Box, Color/Material,
Camera, Light, Collider, скриптовый компонент.

### Фаза 4. Edit / Play — несколько дней
- **Play** — единственное место, где исполняется код.
- Правка сцены во время Play запрещена (как в Unity): иначе получить
  невоспроизводимое состояние.

### Фаза 5. Публикация — несколько дней
- «Опубликовать» → сцена+скрипты → каталог, через существующий
  `play.js`.
- Это главная кнопка продукта: без неё редактор — игрушка.

### Фаза 6. Экспорт в один файл
- `build.py` уже умеет собирать автономный файл — экспорт игр из
  редактора идёт тем же путём.

## 5. Что НЕ делаем

- Компоненты, материалы, шейдеры на уровне Unity — это годы работы.
- Свой язык визуального программирования. BloomScript уже есть.
- Импорт моделей из Blender. Наш движок рисует примитивы и спрайты.
- Мультиплеер. Сервер запрещён по решению владельца.

## 6. Главный риск

Не технический, а продуктовый: **редактор без аудитории мёртв**. Нужен
трафик. Поэтому редактор имеет смысл строить **после** того, как
каталог начнут открывать, иначе он будет сделан в пустоту.
