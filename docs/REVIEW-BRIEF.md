## Текст запроса

Ты получаешь проект на независимую экспертизу. Проект делал другой ИИ
вместе с человеком. Твоя задача — **не подтвердить его работу, а найти
в ней дыры**. Автор уже считает, что всё хорошо; твоя ценность ровно в
том, чтобы этому не поверить.

### Что это за проект

`C:\MPresent` — браузерная платформа 3D-игр на собственном движке.
Состоит из трёх частей:

1. Каталог из 100 игр, каждая написана вручную на собственном движке E3.
2. BloomScript — свой язык программирования, чтобы игрок писал свои игры.
3. NEBULA Studio — визуальный редактор, компилирующий сцену в BloomScript
   и публикующий её в тот же каталог.

Заявленная цель проекта: **стать конкурентом Яндекс Игр**, то есть
платформе, где игроки публикуют свои игры и играют в чужие.

Сборка — три самодостаточных HTML-файла, открываемых двойным щелчком с
диска. Без сервера, без сети, без облачных сервисов.

Технически всё на обычном JavaScript, без сборщиков в рантайме и без
фреймворков. Node и esbuild используются только как инструменты сборки.

### Что читать

Продукт:
- `index.html` (477 КБ, ~6000 строк) — приложение: каталог 100 игр,
  рендер, HUD, ввод. Основной файл продукта.
- `lang.html` (145 КБ) — редактор BloomScript, подсветка,
  автодополнение, selfTest из 173 проверок.
- `studio.html` — страница редактора Studio.
- `src/engine/e3.js` — движок на Canvas 2D: примитивы, проекция,
  отсечение, сортировка от дальнего к ближнему, освещение.
- `src/engine/e3gl.js` — бэкенд WebGL2 поверх того же движка.
- `src/lang/core.js` — интерпретатор BloomScript (лексер, парсер, AST,
  песочница, лимиты).
- `src/lang/runtime.js` — игровая среда, 88 функций движка.
- `src/lang/play.js` — запуск пользовательских игр в каталоге.
- `src/studio/scene.js`, `src/studio/editor.js` — Studio.
- `src/data/store.js` — локальное хранилище с версиями и миграциями.

Инструменты: `build.py`, `tools/all-gates.py`, `tools/e3gl-gate.py`,
`tools/pack.py`, `tools/esbuild.mjs`.

`docs/FILES.md` — описание файлов. Это написано автором, **не верь
на слово, проверь по коду**.

### Как проверить

```
python tools/all-gates.py --light     # 16 проверок, ~30 секунд
python tools/all-gates.py --full      # плюс движок, поведение, 100 игр
python build.py                       # сборка
python tools/pack.py --zip            # пакет для выкладки
```

### Утверждения автора, которые надо проверить

1. «WebGL2 даёт 4,25× к Canvas 2D на 4000 кубов.» Замер сделан в Chrome
   с `--disable-gpu`, то есть видеокарта эмулировалась на процессоре.
   Проверь, честен ли это замер, и оцени, каким будет выигрыш на
   настоящей видеокарте.
2. «Картинка GL и 2D совпадает на 98,5% пикселей.» Проверь сам
   `tools/e3gl-gate.py` — не занижена ли планка сравнения.
3. «Бесконечный цикл в игре не ловился из-за бага; исправлено, регресс
   есть.» Найди баг сам заново в `src/lang/core.js`, потом проверь, что
   гейт `tools/i0-gate.py` действительно ловит и старый, и новый код.
4. «Все гейты проходят, включая 100 игр.» Запусти и убедись сам.

### Известные автору слабые места

Он их нашёл сам, но мог недооценить. Проверь и дополни:

- `index.html` — около 6000 строк, 100 игр в одном файле. Оцени долг.
- `src/engine/time.js` подключён к страницам, но **нигде не
  используется** — мёртвый код в сборке.
- GL-путь включается только по адресу `?gl=1`, по умолчанию выключен.
- `E3.grid` (сетка отсечения) помечен устаревшим: в браузере она
  медленнее линейного прохода в 2,6 раза, в пути GL не читается.
- Кэша статичной геометрии нет: кубы пересобираются из констант каждый
  кадр.
- Тесты проверяют в основном «нарисовалось» и «не упало», но почти не
  проверяют численную корректность физики и поведения.

### Вопросы, на которые нужен ответ

1. **Продукт.** Реально ли этот проект может конкурировать с Яндекс
   Играми? Где именно разрыв и он закрываемый или нет?
2. **Архитектура.** `index.html` на 6000 строк — это нормально для такого
   продукта или расплата за неудачную последовательность решений? Что
   сломалось первым и что чинить дешевле всего.
3. **WebGL2-бэкенд.** Найди в `src/engine/e3gl.js` ошибки, которые
   проявятся на другой машине или другом браузере. Особенно: корректность
   работы с прозрачностью, сортировкой и поведением при изменении размера
   окна.
4. **Интерпретатор.** Найди в `src/lang/core.js` настоящие уязвимости
   песочницы или ошибки, которые выстрелят при необычном коде игрока.
   Не теоретические, а достижимые из пользовательского кода.
5. **Качество.** Найди код, который работает, но написан плохо:
   дублирование, скрытые зависимости, состояние, размазанное между
   файлами.
6. **Что упущено.** Что автор не сделал, но должен был, чтобы проект
   дожил до пользователей?

### Формат ответа

- **Сильные стороны** — с конкретными примерами из кода.
- **Слабые стороны** — с конкретными примерами. Обобщения вроде «не
  оптимально» не интересуют, интересует файл и строка.
- **Найденные баги** — с описанием, как воспроизвести.
- **Что исправить в первую очередь** — порядок по соотношению
  «эффект / стоимость».
- **Честный вердикт** по каждому из трёх вопросов: движок, Studio,
  язык.

Не хвали и не смягчай. Если что-то сделано хорошо — так и напиши, но
ищи основания, а не поводы. Если утверждение выше не подтверждается —
прямо скажи, что оно неверно.
